## 会战指令与图片

群内发送以下指令即可查看会战信息，图片使用本项目现有 WebUI 生成。

| 指令 | 返回内容 |
| --- | --- |
| `状态` | 公会排名、今日出刀、剩余补偿及秒数、Boss 血量、预约 / 申请 / 挂树名单 |
| `今日出刀` / `昨日出刀` | 对应游戏日的出刀分布，使用夜间主题、大字号和 2 倍像素密度 |
| `分数线` | 档位、合计分数、守线公会、会长、人数；省略空档位、奖励和差距 |
| `自动报刀帮助` | 按用途分组的指令帮助图片 |

状态名单显示成员 QQ 头像，加载失败时显示名字首字。暂停监控后显示最后已知进度；“近期入场”来自游戏接口，不代表全部未结算成员。

今日出刀按完整刀计 1、尾刀和补偿刀各计 0.5，每人最多计 3 刀。统计以已记录战报为准，游戏日统一在 **UTC+8 每天 05:00** 切换。

### 代成员操作

在个人会战指令前后加 `@成员`，即可操作该成员；不 @ 时操作本人。例如：

- `进3 @成员`：申请挑战 3 王。
- `不打了 @成员`：取消申请。
- `sl @成员` / `sl? @成员`：记录 / 查询 SL。
- `预约 2 @成员` / `取消预约 2 @成员`：预约 / 取消预约。
- `挂树 3 @成员` / `下树 @成员`：挂树 / 下树。

留言中会去除 @ 代码。清空全体记录的指令仍需管理员权限。

## 补偿刀与返还时间

### 尾刀怎么判定

**自动判为尾刀必须有明确的击杀证据。** 正常刀中途团灭仍记完整刀，补偿刀提前结束仍记补偿刀。

正常刀击杀 Boss 后会计算返秒，并在播报中追加“获得了xxs的返还时间”。补偿刀击杀只消耗已有补偿，**不会再次获得返秒**。

缺少击杀前血量等必要数据时，暂不猜测秒数。后续数据补齐或启动监控时，会重新核对当天记录，但不会重发过去的击杀播报。手动修正优先于自动判定。

### 90 秒满补怎么识别

仅凭“起始时间为 90 秒”，无法区分完整刀和满补。程序会按玩家、按游戏日，结合以下信息核对：

- **每日次数**：完整刀与尾刀合计最多 3 次，补偿刀消耗之前获得的补偿。
- **返秒匹配**：已有补偿的秒数是否与后续战斗的起始时间一致。
- **阵容复用**：当天完整五人阵容相同，或与尚未使用补偿的尾刀阵容重复至少两个角色时，排除新的正常起刀；仍需匹配到可消耗的补偿。

单个角色重复可能来自支援，不作为强制判定依据。只有各个合法解释都得到相同结论时，才自动修正类型；全新阵容、记录缺失等情况可能仍无法确定。程序不会直接把最后一刀改成补偿来凑三刀上限。

### 查询剩余补偿

| 指令 | 查询范围 |
| --- | --- |
| `剩余补偿` / `查补偿` | 全群今日剩余补偿 |
| `我的补偿` | 自己绑定的账号 |
| 上述指令加 `@成员` | 被 @ 成员的账号，沿用已有账号查询权限 |

状态图片中也会显示剩余补偿，按本群当天已记录战报推算，并扣除已使用的补偿。例如：`子非鱼：90s×1、26s×1`。

| 显示内容 | 含义 |
| --- | --- |
| `90s×1` | 可确定还剩一把 90 秒补偿 |
| `待确认：90s×0～1` | 无法确定这把补偿是否已使用 |
| `秒数未知` | 缺少确认秒数的数据；数量是否确定需结合“待确认”标记查看 |
| `无法确认` | 记录不足或存在冲突，无法可靠还原 |

待确认和冲突记录不能直接当作可用补偿。旧数据缺少阵容或原始血量时，也可能无法还原全部满补。

<details>
<summary>返秒计算与漏记补抓的技术说明</summary>

正常刀的返秒公式为：

```text
返秒 = min(90, ceil(110 - 战斗耗时 × 击杀前剩余血量 / 原始伤害))
```

算法参考 [pcr_calculator_plus](https://github.com/watermellye/pcr_calculator_plus/blob/master/pcr_calculator.py)。非合刀击杀等价于剩余时间加 20 秒，上限 90 秒。已唯一确定补偿消费关系时，也可以用后续补偿的实际起始秒数，补全对应尾刀的返秒。

缺少击杀前血量时，监控会按需完整抓取本期战报，每群最多每两分钟尝试一次。恢复血量前需要确认：

- 抓取前后第一页没有变化，分页完整。
- 能看到前一周目同一 Boss 的击杀记录。
- 本周目相关战报均已唯一入库，末尾只有一条确认击杀。
- 配置中的 Boss 满血与游戏当前满血一致。

满足条件后，以满血减去前序有效伤害恢复击杀前血量，再扣除溢出伤害、重算返秒。分页失败、记录缺失、重复、同秒顺序不明或跨阶段满血无法验证时跳过恢复。

补抓会逐页核对已入库记录，再按时间从旧到新入库，不依赖接口的分页顺序。单页或单条详情失败会记录错误，其余记录继续处理，后续扫描重试漏记项。

出刀详情和手动修正统一使用数据库唯一 ID 作为出刀编号，避免同秒战报撞号。本地 `battle_log_id` 同样使用数据库 ID，游戏详情请求仍使用接口原始 ID。

</details>

## 首日满补模式

适用于首日 B/C 阶段留下大量 90 秒补偿、随后在 D 阶段使用的公会。开关按群独立，默认关闭。

| 指令 | 作用 |
| --- | --- |
| `开启首日满补` / `开启首日满补 自动` | 持续开启，每期自动识别首日，无需每月重开 |
| `开启首日满补 YYYY-MM-DD` | 手动指定生效日期 |
| `首日满补状态` | 查看当前设置及生效状态 |
| `关闭首日满补` | 关闭后续特殊判定，不回滚已修正记录 |

群主、管理员或 bot 主人可操作。WebUI 监控状态栏“第几天”旁也有同一个开关，可选择每期自动或手动日期；其他成员只读。设置重启后保留。

开启后，**仅首日将完整刀按补偿刀统计**，并处理该日已入库及延迟取得的战报。确认的正常刀击杀仍记尾刀，识别出的补偿收尾仍记补偿。真实出刀资源依然按“完整刀＋尾刀最多 3 次”推算，不因统计口径改变而额外生成补偿。

其他日期恢复正常判定。此模式是公会约定的统计方式，不能仅凭 90 秒时长证明某刀实际属于补偿。

自动识别需开启国服会战监控，以会战编号匹配现有 Boss 数据源的开赛日程。日程未取得时显示“待识别”，暂按正常规则判定；台服请手动指定日期。旧版已有的手动日期不会自动切换为自动模式。

## 图片功能部署

状态、出刀分布、分数线和帮助图片共用一套截图环境。分数线图片还需开启出刀监控，以取得档线数据。

### 安装与配置

在机器人的 Python 环境中安装截图依赖：

```sh
pip install playwright
python -m playwright install chromium
# Linux 首次部署可用：
# python -m playwright install --with-deps chromium
```

重新构建并启动 `web/` 前端，然后在 `setting.py` 的 `WebSetting` 中配置：

| 配置项 | 说明 |
| --- | --- |
| `status_image_url` | 机器人能访问的截图页地址，默认 `http://127.0.0.1:5173/#/status-image` |
| `status_image_browser_channel` | Windows 已安装 Edge 时，可设为 `"msedge"` |
| `status_image_asset_timeout_ms` | 头像、Boss 图标和字体的等待时间，默认 2000 毫秒，可设 500～10000 |

截图页通过独立浏览器上下文注入本群数据，无需网页登录账号、密码或开放群数据接口；普通浏览器直接打开不会显示群数据。出刀分布截图的夜间主题也只在截图时生效，不改变成员的网页主题设置。

### 速度与失败处理

- 复用浏览器进程，每次截图使用独立上下文；空闲 5 分钟后自动关闭浏览器。
- 帮助图片缓存 5 分钟，内容变化后重新生成；动态战报图片每次重新生成。
- 图片资源等待超时后使用占位样式。网络较慢时可适当调高等待时间。
- 截图失败时，“状态”和帮助回退为文字，“今日出刀 / 昨日出刀”回退为原统计图片，详细原因记入机器人日志。

**一个 QQ 只绑一个游戏账号，绑一次所有群通用**（换公会、进新群都不用重新绑）。

【绑定账号 账号 密码】
【渠绑定账号 login_id token】
【台绑定账号 short_udid udid_viewer_id】

## 🌐 WEBUI 配置说明

网页端（可选功能）首次部署需要修改两处配置，把默认地址换成你自己的：

### 1. `setting.py` → `WebSetting`

| 配置项 | 说明 |
| ------ | ---- |
| `api_host` / `api_port` | 后端 FastAPI 监听地址，默认 `0.0.0.0:12138` 一般无需修改 |
| `web_host` / `web_port` | **`web_host` 请改为你部署机器的内网 IP**（如 `192.168.1.100`），QQ 机器人回复的登录链接会使用该地址；仅本机访问可保持 `127.0.0.1` |
| `api_base` / `web_base` | 接口/页面路径前缀，一般无需修改 |

### 2. `web/.env` → 前端代理的后端地址

```dotenv
# 前后端在同一台机器：保持默认即可
VITE_API_URL=http://localhost:12138
# 机器人后端在另一台机器时，改为该机器的内网 IP，例如：
# VITE_API_URL=http://192.168.1.100:12138
VITE_API_BASE=/kanna_dependency
```

> 前端的启动方式、目录结构与全部接口说明见 [web/README.md](web/README.md)：`npm install` 后 `npm run dev`（开发模式）或 `npm run build`（生产构建）。
